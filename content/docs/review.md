A review answers three questions: does the project fit LOADOUT, is the work you submitted valid, and how strong is the technical contribution you can show?

## What reviewers check {#stages}

| Stage | The question |
| --- | --- |
| Project fit | Does the technical core belong in LOADOUT? |
| Validity | Do the files, journals, time and credits back up what you submitted? |
| Quality | How strong is the approved work across the four dimensions? |

A project can be useful and still sit outside LOADOUT's focus. A project that fits can also need more evidence before its work is approved.

## Four quality dimensions {#quality}

| Dimension | The question |
| --- | --- |
| Originality | What's new in how you built it, or in the limits you worked within? |
| Technical Depth | What hard problem did you solve, and how well do you understand it? |
| Execution | Does it work for what it's meant to do? |
| Documentation | Could another builder understand it, check it or reproduce it? |

Quality feeds into the Ore multiplier. The exact scoring and payout values aren't set, so there's no calculator here yet.

## AI use and team projects {#authorship}

Reviewers need to see what you built yourself. Declare AI help, borrowed code, dependencies and each person's part.

[AI & team contributions](/docs/ai-teams) covers what's expected.

## Feedback and revisions {#feedback}

Good feedback names the decision, the work it covers, and anything missing or worth improving. A request for changes isn't a final yes.

If you revise a ship, say what changed and add the evidence you were asked for. Don't submit the same work twice hoping for a different award.

## Questions about a decision

Builders should be able to question decisions about fit, approved work, quality or track split. The way to do that, and how long it takes, isn't published yet.

Keep the review reference and say which decision you mean. **#loadout-help** can clear things up, but it can't promise an outcome.
